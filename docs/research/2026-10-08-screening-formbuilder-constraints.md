# Research: form-builder + Payload admin constraints for screening review

Date: 2026-10-08 · Ticket: `.scratch/m2-closeout/issues/01-screening-formbuilder-constraints.md`
Versions verified: `payload` 3.84.1, `@payloadcms/plugin-form-builder` 3.84.1, `@payloadcms/ui` 3.84.1 (as installed under `apps/web/node_modules`, resolved from the pnpm store). Primary sources: installed package source, repo code, official docs at payloadcms.com.

Legend: **[V]** = verified fact (file path / URL cited) · **[I]** = inference from verified mechanics.

## Q1 — Submission lifecycle: adding a review-status select under drafts + autosave + versions

### What the plugin actually lets you override

- **[V]** `formSubmissionOverrides` accepts `{ fields?: FieldsOverride } & Partial<Omit<CollectionConfig, 'fields'>>` — every collection-config key except a literal `fields` array; `fields` must be a function receiving `{ defaultFields }` (`apps/web/node_modules/@payloadcms/plugin-form-builder/dist/types.d.ts`, `FieldsOverride`).
- **[V]** If `formSubmissionOverrides.fields` is present but **not a function**, the plugin silently ignores it and falls back to its own `defaultFields` (dropping nothing of yours, but adding nothing either) — `plugin-form-builder/dist/collections/FormSubmissions/index.js:102-104`. So the only sanctioned way to add `SCREENING_STATUS` is inside the existing `formSubmissionFieldsOverrides(defaultFields)` function — exactly how today's `isApproved`/`isRejected` checkboxes are added (`apps/web/src/lib/plugins/forms/screening/overrides/formSubmissions.ts:46-177`).
- **[V]** The plugin's default submission fields are only `form` (relationship, required, with an existence validator) + `submissionData` (array of field/value) (+ optional upload/payment fields); `versions`, `access`, `admin`, `hooks` pass through the spread untouched (`plugin-form-builder/dist/collections/FormSubmissions/index.js:89-119`).
- **[V]** `SCREENING_STATUS` (PENDING/APPROVED/REJECTED/NEEDS_REVIEW) already exists in `packages/enums/src/index.ts:108-113` and is referenced nowhere else — free to become the select's options.

### Drafts/versions mechanics that constrain the status field (verified against payload 3.84.1 source)

- **[V]** Updates read and merge onto the **latest version** (an in-flight draft wins over the published snapshot): `payload/dist/collections/operations/updateByID.js` calls `getLatestCollectionVersion` (`payload/dist/versions/getLatestCollectionVersion.js`).
- **[V]** Every save writes a **full-document version snapshot**; publishing (`_status: 'published'` in the update data, no `draft: true`) writes the merged doc to the main collection as published (`payload/dist/collections/operations/utilities/update.js`, `isSavingDraft` logic + `saveVersion`). Docs: "the main collection will be updated with the published status" (https://payloadcms.com/docs/versions/drafts).
- **[V]** Draft saves **skip required-field validation** by default: `skipValidation: isSavingDraft && !hasDraftValidationEnabled(collectionConfig)` (`payload/dist/collections/operations/utilities/update.js:146-149`; helper in `payload/dist/utilities/getVersionsConfig.js`). `versions.drafts.validate: true` re-enables it. This is why mobile can create a draft with `submittedAt: undefined!` even though `submittedAt` is `required: true` (`apps/mobile/features/donor-screening/lib/api/mutate/submission.ts:23-31`, `formSubmissions.ts:66-72`). Docs note the bypass needs the `draft: true` request param, not `_status: 'draft'` (https://payloadcms.com/docs/versions/drafts).
- **[V]** Default reads return the published doc and ignore drafts; `draft: true` returns the most recent version (https://payloadcms.com/docs/versions/drafts). The org-facing access policy already relies on this (`authenticatedAndPublished`, `submitterOrAssociatedOrgOrAdmin` in `apps/web/src/lib/plugins/forms/screening/access.ts`).
- **[V]** **Field-level access control exists and silently preserves prior values**: when `field.access.update` returns false, the incoming value is *deleted* from the update payload and the field falls back to the original doc's value — no error thrown (`payload/dist/fields/hooks/beforeValidate/promise.js:216-235`, fallback via `getFallbackValue` cloning `siblingDoc[field.name]`). Docs: "the operation will not throw an error however the field will be omitted from the update operation and the value will remain unchanged" (https://payloadcms.com/docs/access-control/fields). Field access is boolean-only (no where-constraints).

### The two failure modes the ticket asks about

1. **Donor editing a draft must not reset an approval.**
   - **[V]** Against *direct writes*: field-level `access: { update: admin-only }` on the status select makes any donor-submitted status change a no-op that keeps the previous value (sources above). This works through REST, the admin panel, and the plugin path alike.
   - **[I]** Against *snapshot clobbering*: field access only strips **incoming** values. Because updates merge onto the **latest version** and versions are full snapshots, a donor whose in-flight draft was forked *before* a reviewer approved will, on re-publish, write the draft's stale status (e.g. PENDING) over the published APPROVED — field access cannot see or stop this (the donor never sends a status value; the stale one rides along in the snapshot). Safe sequence (no in-flight donor draft when the reviewer approves) inherits APPROVED correctly.
2. **Does re-publishing resurrect old field values?**
   - **[V]** Publishing the current draft: yes, wholesale — the draft snapshot becomes the published doc (`update.js` + docs above). Any field the reviewer changed on the published version after the draft forked reverts.
   - **[V]** Explicit version restore: `restoreVersion` runs a full old snapshot back through the update pipeline (`payload/dist/collections/operations/restoreVersion.js`); exposed in the admin version view; bounded by `versions.maxPerDoc: 10` (`apps/web/src/lib/plugins/forms/screening/index.ts:63-66`).

### Consequence for the redesign (inference, design choice to make in the spec)

- **[I]** Field-level admin-only `access.update` on `SCREENING_STATUS` is necessary but not sufficient. The spec should pair it with one of:
  (a) a collection `beforeChange` hook on publish operations that re-reads the currently published version (`where: { 'version._status': equals published }` against the versions table) and force-carries its `SCREENING_STATUS`/`reviewedBy`/`reviewedAt` into `data` before the new version is written;
  (b) a policy that any donor re-publish auto-demotes status to `NEEDS_REVIEW` (same hook, simpler semantics: "edits invalidate approval");
  (c) locking: donor `update` access returns a where-policy that excludes approved docs (collection access where-policies filter on the doc itself; donors get `{ status: { not_equals: 'APPROVED' } }`, admins get `true`).
- **[I]** Keep `versions.drafts.validate` off (default) or the mobile draft flow (create without `submittedAt`) starts failing required-field validation.
- **[I]** Migration note: replace the `isApproved`/`isRejected` pair plus four stamped fields (`approvedAt/By`, `rejectedAt/By`, `formSubmissions.ts:74-176`) with one select + one `reviewedAt`/`reviewedBy` pair; existing boolean data must be mapped to enum values. The form's submissions join view references `isApproved` in `defaultColumns` and must be updated (`overrides/form.ts:93-101`).

## Q2 — Platform-admin review queue in the Payload admin panel: native vs custom

### Native (no custom code)

- **[V]** List-view filtering, column choice, sorting: the admin list view has a native where-filter builder and column/sort pickers per collection; config-level defaults via `admin.defaultColumns`, `useAsTitle`, `defaultSort`, `listSearchableFields`, plus `baseFilter` (https://payloadcms.com/docs/configuration/collections). The submissions collection already sets `defaultColumns: ['submitterEmail', 'form', 'submittedAt', '_status']` and `useAsTitle: 'submitterEmail'` (`screening/index.ts:57-61`).
- **[V]** **Query presets** (saved filters): users can save a list view's `where` filters + columns + groupBy as reusable, optionally shared presets (constraints: `onlyMe` / `everyone` / `specificUsers`; `isShared` flag) — `payload/dist/query-presets/config.js` + `types.d.ts` (internal `payload-query-presets` collection). **Opt-in per collection**: the presets UI is disabled unless `collection.admin.enableQueryPresets === true` — `@payloadcms/ui/dist/views/List/index.js:186` (`disableQueryPresets: collectionConfig?.enableQueryPresets !== true || disableQueryPresets`); sanitize side at `payload/dist/config/sanitize.js:202`. The submissions collection does not set it today — one line to enable, then admins can save a "PENDING review" queue view themselves. (Introduced upstream in v3.31.0 — secondary source, allaboutpayload.com; the installed 3.84.1 code is the authority.)
- **[V]** **Bulk actions on selected rows**: native `EditMany` (bulk-edit drawer rendering the collection's fields, submits `PATCH` with `skipValidation: true`), `PublishMany`, `UnpublishMany`, `DeleteMany`, `RestoreMany`, plus select-all-across-pages — `@payloadcms/ui/dist/views/List/ListSelection/index.js` and `dist/elements/{EditMany,PublishMany,UnpublishMany,DeleteMany,RestoreMany}/`. Toggleable via `admin.disableBulkEdit` / `disableBulkDelete`; gated by update/delete permissions (https://payloadcms.com/docs/configuration/collections).
- **[I]** Bulk edit routes through the normal REST update path, so a `SCREENING_STATUS` select appears in the EditMany drawer and each per-doc update passes through collection/field access and `beforeChange`/`afterChange` hooks — bulk-approve therefore respects the same guards as single-doc review. (Mechanism verified for the drawer's PATCH; per-doc access pass-through inferred from the standard update pipeline.)
- **[V]** Draft/published visibility: `_status` is a native filter and column; the org-facing join field on the form already filters `_status equals published` (`overrides/form.ts:100`).

### Custom-view work (needed only beyond the above)

- **[V]** Custom components: per-collection list slots `admin.components.{beforeList, beforeListTable, afterList, afterListTable, Description}` and edit-view slots (`beforeDocumentControls`, `editMenuItems`, `PreviewButton`, `PublishButton`, …) — `payload/dist/collections/config/types.d.ts:261-340`; full `Table` replacement and `listMenuItems` via `ListViewSlots` (`payload/dist/admin/views/list.d.ts`).
- **[V]** Custom views: new admin pages via `admin.components.views` at root, collection, or global scope — `{ Component, path (path-to-regexp, leading `/`), exact, strict, meta }`; adding any custom key registers a new route; server components receive `initPageResult` (req, payload, permissions); "All Custom Views are public by default", handle auth yourself (https://payloadcms.com/docs/custom-components/custom-views; types at `payload/dist/config/types.d.ts:746-752`, `collections/config/types.d.ts:315-330`).
- **[V]** There is **no native per-row custom action slot** in the list view (no `RowActions` component slot in collection config — only Blocks have `RowActions`; grep across `payload/dist` + `@payloadcms/ui/dist`), so per-row "Approve/Reject" buttons require replacing/extending the list `Table` component.
- **[I]** Verdict for the spec: a functional platform-admin queue (filter by status → open → set status, with bulk approve) is achievable with **zero custom views**: `enableQueryPresets: true` + `defaultColumns` including status + native bulk edit. Custom work is only warranted for a bespoke triage screen (submission answers rendered inline, one-click approve/reject, keyboard flow) — a custom collection view is the natural shape if wanted later.

## Q3 — Plugin submission hooks: what they allow for status transitions + notifications

- **[V]** Hook merge order is fixed: the plugin always **prepends** its own hooks to yours — `beforeChange: [handleUploads?, createCharge, ...yours]`, `afterChange: [sendEmail, ...yours]` (`plugin-form-builder/dist/collections/FormSubmissions/index.js:105-118`). You cannot remove or reorder the plugin's hooks via overrides; every other hook key (`beforeValidate`, `afterRead`, …) spreads through untouched.
- **[V]** `createCharge` is a no-op unless `handlePayment` is configured (this repo doesn't) — `dist/collections/FormSubmissions/hooks/createCharge.js:4-9`. `handleUploads` only registers when `uploadCollections` is set (not set here).
- **[V]** `sendEmail` fires **only on `operation === 'create'`**, reads the related form, and sends only if `form.emails` is a non-empty array; `emailTo` falls back to `defaultToEmail` (set to `lactalinkph@gmail.com` in this repo) then `payload.email.defaultFromAddress`; supports `{{field}}` / `{{*}}` placeholder interpolation from submissionData; the whole thing is try/catch'd — email failure never fails the write — `dist/collections/FormSubmissions/hooks/sendEmail.js:4-74`. The repo's `formFieldsOverrides` keeps the `emails` field intact on the Form (`overrides/form.ts` filters out only `confirmationType`/`confirmationMessage`/`redirect`).
- **[V]** `beforeEmail` (plugin config option) receives the formatted email list before sending and can rewrite or empty it — returning `[]` effectively suppresses (`sendEmail.js:45-48`; type `BeforeEmail` in `dist/types.d.ts`).
- **[V]** **Timing trap with this repo's flow**: mobile *creates* the submission as a draft (`draft: true`, `submissionData: []`) and publishes later via update (`apps/mobile/features/donor-screening/lib/api/mutate/submission.ts:8-32, 69-79`). `sendEmail` keys on `operation === 'create'`, so with `form.emails` configured the plugin's email fires at **empty-draft creation**, not at publish — and never on the publish update or any later status change.
- **[I]** Consequences: (1) "notify reviewer on submission" must be a custom `afterChange` hook (yours run after `sendEmail` in the same chain) gated on publish transitions — e.g. detect `previousDoc._status !== 'published' && doc._status === 'published'`; (2) approve/reject notifications cannot use the plugin's email hook at all — wire them in the same custom `afterChange` on `SCREENING_STATUS` transitions (or in field/collection hooks), sending via `req.payload.sendEmail` (Resend is already installed: `@payloadcms/email-resend` in `apps/web/package.json`); (3) consider `beforeEmail` to suppress the plugin's create-time email if `form.emails` gets used, since in this flow it would fire on empty drafts.
- **[V]** Status-transition enforcement point: collection-level `beforeChange` hooks added via `formSubmissionOverrides.hooks` receive `{ data, originalDoc, operation, req }` and their return value replaces the data written — the standard place to stamp `reviewedAt`/`reviewedBy` from `req.user` on status change (same pattern as today's field hooks, `formSubmissions.ts:96-125`, but collection-level so it sees sibling data regardless of which fields the client sent).

## Summary table

| Need | Support | Effort |
|---|---|---|
| Add single `SCREENING_STATUS` select | Via `formSubmissionOverrides.fields` fn (the only way) | trivial — replaces checkbox pair |
| Donor can't set status | Field-level `access.update` (silent keep-old-value) | small |
| Donor re-publish clobbering approval | NOT covered natively — needs beforeChange carry-forward / auto-demote / lock policy | medium — spec decision |
| Admin queue list (filter+columns) | Native list filters + `defaultColumns` | config only |
| Saved/shared queue views | Native **query presets** — requires `enableQueryPresets: true` (off today) | one line |
| Bulk approve | Native `EditMany` bulk-edit drawer (goes through access+hooks) | none |
| Per-row approve/reject buttons | No native row-action slot — custom Table/ListView or custom view | custom work |
| Reviewer/donor notifications | Plugin email hook fires only on create (empty draft here) — custom afterChange + `payload.sendEmail` | small-medium |
